## 5分で見られるおすすめの操作

1. **admin** でログインし、**ダッシュボード**で見込み金額・受注残・粗利見込みと「要対応」の一覧を確認する
2. **見込み客・案件**で工事No **A2610001** をクリック → 案件照会画面で、再見積(-01、-02)の版と、カテゴリ別の見積内容を見る
3. 見積内容の **カテゴリ名(例:解体工事 ✎)をクリック** → 単価を変えて保存 → 「再見積として保存」で **-03** が追加される
4. 「受注確定」で採用する版を選ぶ → 番号が枝番なしの **A2610001** になり、採用しなかった版は **ごみ箱** へ
5. **工程会議**で施工担当(自社職長/協力業者)と確定着工日を入力 → **変更履歴**に「変更前 → 変更後」が記録されていることを確認する
6. **見積書** / **請求書** ボタンで帳票を新しいタブに開き、「PDFで保存」を試す
7. **見込み客・案件**の「Excel見積書から登録」で、[サンプルのExcel見積書](estimate_sample.xlsx)を読み込んで案件と見積を自動登録する

## 作った背景

解体工事会社の総務事務として、販売管理システムの導入検討に関わりました。
市販の販売管理システムは物販向けのものが多く、解体工事業に特有の次のような業務に合いにくいという課題がありました。

- 一戸建てなどの**小規模解体**と、公共工事・RC造などの**大規模解体**で、営業の進め方や金額規模が大きく違う
- 見積の提出が受注の前提で、問合せ・紹介・入札情報など**見込み客の段階**から追いかけたい
- 値引きや仕様変更で**再見積**が何度も出るため、版を管理したい
- 請求は工事の進み具合に応じた**出来高請求**、協力業者への支払も**出来高ベース**
- 産業廃棄物の**電子マニフェスト(JWNET・e-reverse)**の登録漏れを防ぎたい
- 工事Noの付け方や、工程会議での着工日の決め方など、**社内の運用ルール**をそのまま反映したい

これらを1本の業務の流れとしてつなぐことを目標に、業務の洗い出し・要件整理・運用ルール(番号体系など)の設計を自分で行い、実装には生成AI(Claude)を活用しました。画面ごとの動作確認と、実務に合わせた仕様の修正を繰り返して仕上げています。

## 主な機能

### 営業・見積

| 機能 | 内容 |
|---|---|
| 見込み客・案件 | 顧客・工事名・構造・面積・担当部隊(小規模解体/大規模・公共)・営業担当・流入経路・受注確度・着工/完工予定日で管理 |
| 見積(版管理) | 明細をカテゴリ(仮設工事・解体工事・産廃処分・付帯工事・その他)別に管理。未受注の間は「工事No-枝番」(A2611001-01、-02…)で再見積を管理 |
| 見積日の確定 | 見積日は見積書を**発行(PDF化)した日**で確定。発行後の版は変更できず、変更は再見積で行う |
| 案件照会 | 工事Noをクリックすると、案件情報・見積の全版・カテゴリ別の見積内容・工事・請求・支払をまとめて表示 |
| カテゴリ別の再見積 | 見積内容のカテゴリ名をクリックしてカテゴリごとに編集 → 保存を繰り返し、最後に「再見積として保存」で新しい版を追加 |
| 受注確定 | 採用する版を選ぶと枝番を外して工事Noのみになる。採用しなかった版はごみ箱へ(元に戻せる)。失注した番号は欠番 |
| Excel見積書の読込 | `estimate_sample.xlsx` の書式のExcelを読み込み、内容を確認してから案件と見積を自動登録。既存案件への再見積としての取り込みも可能 |

### 工事・請求・支払

| 機能 | 内容 |
|---|---|
| 受注工事・電子契約 | 契約金額・工期(見積時の予定/工程会議で確定した日)・出来高・請求済額・協力業者発注額・粗利率を一覧。電子契約の送付/締結状況を管理 |
| 工程会議 | 施工担当を「自社職長」「協力業者」の区分付きで決定(区分に応じて職長名・協力業者名を候補表示)。見積時の着工/完工予定日とは別に、工程会議で着工日・完工日を確定(未来の日付も可、確定後も随時変更可)。予定との差(○日遅れ等)を自動表示 |
| 出来高請求 | 累計出来高率を入力すると「契約額 × 累計出来高率 − 前回までの請求額」で今回請求額を自動計算 |
| 協力業者・出来高支払 | 工事ごとの発注登録と、出来高に応じた支払額の自動計算(発注額 × 累計出来高率 − 既払額)。支払一覧CSV |
| マニフェスト | 廃棄物の種類・数量・方式・番号・状態を記録。未登録分をダッシュボードに警告し、入力作業用CSVを出力 |
| 帳票 | 「見積書」「請求書」ボタンで新しいタブに帳票を表示し、「印刷する」「PDFで保存」で出力 |

### 管理

| 機能 | 内容 |
|---|---|
| ダッシュボード | 商談中の見込み金額・受注残・今月の出来高請求・協力業者の未払残・粗利見込み、部隊別グラフ、月別請求グラフ、要対応リスト |
| ログイン・アカウント | 自己登録と管理者による登録、ログイン、職種カテゴリ(管理者・営業スタッフ・職長・作業員・事務スタッフ・役員)、停止・パスワード再設定 |
| 権限 | 職種カテゴリで画面の表示を制御(現在は変更履歴を管理者・役員のみに限定。その他の権限は今後設定予定) |
| 変更履歴 | 保存のたびに変更前後を自動で比較し、いつ・誰が・何を・どう変えたかを記録。対象・操作者・期間・キーワードで絞り込み、CSV出力。案件照会画面にも案件ごとの履歴を表示 |
| 設定 | 支店と支店記号の追加・編集、工事Noの採番ルールの選択と確定(ロック) |
| ごみ箱 | 受注確定で不採用になった版や削除した見積を保管し、元に戻せる |
| データ管理 | JSONでのバックアップ/読込、サンプルデータへの初期化 |

## 工事No・見積番号の採番ルール

| 項目 | 内容 |
|---|---|
| 工事No | 「支店記号 + yymm + 全社共通の3桁連番」を最初の見積作成時に自動採番(例:A2611001) |
| 支店記号 | 本社 A、東京支店 T。見積の発行支店で自動的に振り分け。設定画面で追加できる |
| 連番 | 支店をまたいだ全社共通の通し番号(A2611001 の次は T2611002)。毎月1日に001へ戻る。月999件まで、900件を超えると画面で注意表示 |
| 見積番号 | 未契約の間は工事Noに枝番を付ける(A2611001-01、-02)。受注確定で採用した版は工事Noのみ |
| 失注 | 番号は欠番のままとし、再利用しない |
| 旧番号 | A2154、T2036 などの旧形式はそのまま残し、一覧は作成日順に並べて新旧が混ざっても正しく並ぶ |
| ルールの切替 | 決算期方式(例:A19-0001、期首月にリセット)も選択可能。稼働後に形式を変えると新旧が混在するため、稼働開始時に確定してロックする |

## 工夫した点

- **運用ルールを仕様に落とし込む**:番号体系(全社共通連番・月次リセット・枝番・欠番・旧番号との混在)や、「見積時の予定日」と「工程会議で確定した日」の区別など、現場の決めごとを整理してから実装した
- **業務の流れでデータをつなぐ**:案件 → 見積 → 受注確定 → 工程会議 → 請求・発注・マニフェストが連動し、状態(見込み/見積提出/受注/失注、着工前/施工中/完工)が自動で切り替わる
- **金額の整合性を守る**:累計出来高率は前回より大きい値しか入力できず、請求・支払の取消は最新分のみ。発行済みの見積は変更できず、再見積で版を分ける
- **「要対応」の自動抽出**:電子契約の未締結、施工担当の未定、着工日の未確定、完工日の超過、マニフェスト未登録、今月の出来高請求の未作成、見積の未発行・期限切れを一覧化
- **記録漏れの起きない変更履歴**:操作ごとに記録処理を書くのではなく、保存のたびに直前の状態と比較して差分を自動で記録する仕組みにした
- **Excelからの移行を想定**:使い慣れたExcel見積書をそのまま取り込めるようにして二重入力をなくした。見出しの文字で項目を探すため行位置が多少ずれても読め、読めない値は「確認事項」として表示する
- **スマートフォン対応**:画面幅に合わせて、一覧表は項目名付きのカード表示、入力画面は全画面表示、メニューは折りたたみ式に切り替わる。現場や外出先からも見積・工程を確認できる
- **導入しやすさ**:HTML/CSS/JavaScriptの1ファイル構成で、サーバーやインストールは不要

## 技術

| 項目 | 内容 |
|---|---|
| 構成 | HTML / CSS / JavaScript のみ(外部ライブラリ不使用・1ファイル) |
| 公開 | GitHub Pages |
| データ保存 | ブラウザの localStorage(外部への送信なし) |
| PDF出力 | 帳票をCanvasに描画し、PDFファイルをブラウザ内で組み立て(日本語・複数ページ対応、オフラインで動作) |
| Excel読込 | ブラウザ標準機能(DecompressionStream・DOMParser)で .xlsx を解析。ファイルは外部に送信しない |
| パスワード | SHA-256 でハッシュ化して保存 |

**デモとしての制約:** ログイン・採番・変更履歴はブラウザ内で完結する仕組みのため、厳密なセキュリティや改ざん防止はありません。本番運用では、サーバー側の認証、データベースのトランザクションによる採番(同時作成での重複防止)、追記専用の履歴テーブルを想定しています。
